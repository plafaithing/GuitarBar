## 2026-10-29 二期执行（环境与代理协作）

- **场景 1**：子代理跑 `flutter pub add "image:^4.3.0"` 后 pubspec 实际写入 `image: 4.3.0`（精确 pin），`^` 在命令传参中丢失。
- **规则 1**：加依赖不使用 `flutter pub add <约束>`，直接编辑 `pubspec.yaml` 加行再 `flutter pub get`；或加完必须核对 pubspec 实际内容。
- **场景 2**：计划里给出的代码在我方（控制者）写计划时无法验证第三方包运行时行为——image 4.x 的 decodeImage 对垃圾输入抛 RangeError（Error 非 Exception）而非返回 null；drift text 模式 datetime 读裸 ISO 串会追加 Z 按 UTC 解释。
- **规则 2**：计划代码里凡调用第三方包的边界行为，都按"胶水可调"预授权并要求实现者读包源码对齐后汇报；计划文档同步在任务里写明该预授权范围。
- **场景 3**（审查侧）：质量审查对 image 包垃圾输入走哪个分支仅凭源码推断下了结论，探针实测证伪（`[1,2,3]` 同样走 catch 分支而非 null 分支）。
- **规则 3**：对第三方包边界行为的判断，探针实测优先于源码推断——写结论前先跑一次。
- **场景 4**（计划编写侧）：给"每卡独立 in-flight 态"的指令若只给单字段思路（String? _testingId），实现者会照做——单字段锁不住并发的每卡状态。计划/修复指令中涉及"N 个对象各自独立进行中"的状态，直接指名集合类型（Set）。
- **规则 4**：描述并发/多对象状态时，指令要写到数据结构层面（Set/Map per-key），不能停在"加个状态"层面——实现者会按字面执行。

## 2026-11-01 教训 4 重犯（PowerShell 管道毁文件）

- **场景 4b**：即使替换 pattern 是无操作（match 不到原文写回），`Get-Content | -replace | Set-Content` 重写 UTF-8 文件仍引入 532 个语法破坏（编码/换行损伤），且误用 `git checkout --` 回滚时把未提交的本轮编辑一并丢失，被迫完整重放。
- **规则 4（强化）**：对项目文件**任何形式**的 PowerShell 写操作（即使"只是写回原内容"）都禁止——改文件只用 Edit/Write 工具。发现管道破坏后修复顺序：先 `git diff --stat` 评估 → 只回滚确认损坏的文件 → 盘点未提交改动损失清单 → 逐项重放。

## 2026-10-30 二期走查（二进制常量）

- **场景 5**：Task 8 计划里"手写 1×1 白 PNG 字节常量"实测是坏图（image 包解码 null，API 报 1210 图片解析错误），走查第一现场暴露。
- **教训**：二进制/校验和类常量不可手编——手写 70 字节 PNG 里 IDAT CRC 等环节极易错，且测试不真解码就发现不了。
- **规则 5**：凡需要内嵌图片/二进制常量的，一律运行时用库生成（如 image 包 encodePng），或在计划中要求实现者现场生成并本地解码验证后再用；禁止在计划文档里手写字节序列。

## 2026-10-31 二期走查（跨体系弦号语义）

- **场景 6**：gpx 弦号公式 IR=gp+1 造成谱面上下镜像 + 播放音高 E2↔E4 全反（用户听感"大部分音不准"）。根因：gpif/alphaTab 的 string 1 = **最粗低音弦**，GuitarBar IR 的 string 1 = **最细高音弦**——两体系"从哪头数"相反，而参考实现（alphaTab）与目标体系（IR）的语义差异被"公式一致"的表象掩盖。正确公式 IR = 6 - gp。
- **教训**：移植外部库的格式知识时，**字段语义必须按目标体系重新核对**，不能假设编号方向一致；尤其 string/fret/track 这类"从 0 还是从 1、从高音还是从低音数"的约定，各体系传统不同（GP 系从低音数、MIDI/吉他谱惯例从高音数）。
- **规则 6**：格式移植的第一条对账断言应是**端到端音高**（弦+品+调弦 → 频率对照原版），而不是"字段值一致"——字段值一致可能掩盖语义反转。用户的耳朵是最快的仲裁者：他说"音不准+谱面反"两个症状同时出现，就该立刻怀疑弦号语义而非音色。

## 2026-10-31 走查（AI 识谱放弃决策）

- **场景 7**：AI 识谱三轮对账 7.4%→13.9%→5.6%（弦号不稳定、节奏精度不可达）；业界调研确认 OMR 全是多阶段几何流水线（视觉大模型无符干/符尾几何感知）→ 用户决策放弃 AI 通道，改纯查看器。
- **教训**：端到端对账探针（识谱 IR vs gpx 原版逐音 diff）是评估识别质量的最有效工具——三轮各 2 分钟就暴露了弦号偏移、声部丢失、节奏错误三个独立问题。
- **场景 8**：子代理 `git add -A` 把含 API key 的探针文件入库（协调者创建的探针忘了先删）。
- **规则 7**：凡创建含密钥/敏感数据的临时探针文件，协调者必须**先删再派代理**——子代理会按指令 `git add -A` 一并入库。探针文件命名统一带 `probe_` 前缀 + 结束立即删除。

## 2026-11-01 Ghidra headless 长任务（用户纠正：不要干等）

- **场景 11**：Ghidra headless 首跑即失败（`Negative delay`）——`-analysisTimeoutPerFile` 单位是**秒**，我按毫秒传 3600000 导致 int 溢出；失败后没看输出就干等完成通知，直到用户问"还在分析么"才发现。且此前两次后台任务（下载/分析）被系统内存压力静默清理，被动等通知全程黑盒。

## 2026-11-03 重命名空格校验返工

- 错误：用户说"名字不支持空格"，我直接实现为"任意位置禁空格"，实际意图是"两侧非空、内部可空格"——返工一次（校验+测试全改）。

## 2026-11-04 关闭卡死实锤与守护误杀

- 错误链 1：「播放后关闭卡死」最初以为是打卡挂——close-log.txt（关闭步骤打点落盘）实锤 exit(0) 已调用、进程仍不死：**exit() 的 C 终止序列本身挂死**（soloud 播放后 native 清理钩子死锁）。现场佐证：taskkill /F 都杀不动的僵尸（"no running instance"却还在进程表）。
- 错误链 2：守护 v1 做成常驻心跳（0.7s ping 主线程），把**启动时 5s 同步初始化段**误判为卡死，刚启动的应用被强杀——用户"打开后自己就关了"。
- 规则 15：**关闭类守护必须"事件武装"**（收到关闭信号才开始计时强杀），不做常驻心跳——常驻心跳无法区分"卡死"与"合法的长同步段"（启动初始化/渲染）。
- 规则 16：**dart:io exit() 不保证终止进程**（native atexit 可挂）——必须死的场景用 TerminateProcess（lib/core/hard_exit.dart）。
- 方法论：关闭路径从第一天就打点落盘日志，本次实锤全靠它；"async/timeout 守卫"只保护 Dart 层，跨 FFI/native 边界的挂死要换武器。

## 2026-11-11 widget 探针假时钟挂死（连音修复验证轮）
- 错误链：golden 探针连跑三次各挂 5-10 分钟超时——根因是 **TestWidgetsFlutterBinding 假时钟 zone 内真实异步（File IO / toImage 编码 / matchesGoldenFile 捕获）永不完成**，每轮都在等一个假时钟下不会 resolve 的 Future。
- 规则 17：**widget 测试里一切真实异步 IO 必须 tester.runAsync 包裹**（文件写、toImage+toByteData、golden 捕获）；matchesGoldenFile 在本项目环境同样挂死，视觉验证探针一律用 runAsync + File.writeAsBytes 直写 PNG。
- 方法论：探针测试超时先查"假时钟 vs 真实异步"，不是查业务代码——GOLDEN_BYTES 已打印还挂死 = 打印点之后的 await 在假 zone 里。

## 2026-11-16 数字重叠多轮复现（用户铁律：数字不重叠）
- 场景：折行/拥挤/dup 多轮修复后，用户仍反复发现数字重叠（"很多次改完之后发现多数字重叠"）——每轮修复只验证了当轮引入的改动面，**没有常驻的重叠探针兜底**。
- 规则 18：**任何排布/标注改动后必须跑重叠探针**（按 paint 同款墨宽几何算 label 盒相交，覆盖真实曲库全量），绿灯才算过；新增展示形态（括号/泛音/字母）必须同步进探针的墨宽模型与 tab_layout.inkHalf，漏一处探针就失真。
- 规则 19：**修复类改动跑真谱量化，不能只跑测试套**（合成 fixture 不含真谱的密度分布）——探针谱集 = 用户实际导入曲库（LAS/Flower/Distance/月下之恋/Prologue 等）。

## 2026-11-16 探针度量字体失真（Ahem 虚胖 2 倍）
- 场景：探针残类 4 处怎么修都放不下——m25 一条弦 7 连 "(2)" 括号（0.25 拍距）需 302px 谱面只有 200px。根因：测试环境 TextPainter 无 family → Ahem（**每字形 = 1em**），"(2)" 测出 42px；生产 Windows 引擎默认 Segoe UI "(2)" 仅 ~19px——**整个排布管线与探针在用假字体度量真实产品的铁律**。
- 规则 20：**谱面 canvas 文字必须显式请求主题字体**（tab_view._text 统一注入 kUiFontFamily + fallback，tab_layout._measureInk 同款——两处口径漂移即重叠）；**布局/渲染类测试必须 FontLoader 加载生产字体文件**（msyh.ttc/msyhbd.ttc，真实 family 名无冲突；'Ahem' 名下加载会被内建测试字体压住不生效）。字体缺失时度量退回测试默认，探针口径偏保守不偏松。

## 2026-11-16 排布趟序与亏空判据（左推趟引入的连锁）
- 场景 1：repeat 保护趟（repeatStart +22 组移）跑在拥挤趟**之后**，把 crowd 已按链排好的净空吃掉（gtp 残类 "(2)"×"2" 恒 17px：crowd 推到 +29 后 repeat 把首组 +12 压回）。
- 规则 21a：**移动类趟（边界保护/符号间距）必须在链式趟（crowd）之前**——链趟以移后位置为基准，净空在链内重建；链后再移 = 复原重叠。
- 场景 2：左推趟 ② 用 `p.x+gap-f.x` 判前驱亏空，把拥挤趟的 x 序倒置对（链右推被界钳后后组越过前组、dist=81 无重叠）误判成巨亏空，级联把整条括号链拉到左线帽制造**新**重叠。
- 规则 21b：**亏空判据用实际墨距** `dist=|f.x-p.x|`，`dist ≥ gap` 不推——倒置但墨距已足的对是合法状态；dist<gap 才推前驱左移（倒置且重叠时顺带复位时序）。

## 2026-11-17 折行判据口径差连环爆（全量探针实证）
- 场景：全量探针（158 库 3376 文件）首轮 44735 违例。修复中**四处判据与实际排布趟的口径差**各爆一轮：①rowFits 的链模拟漏**行首贴线保护偏移**（余量 1.1px < 偏移 3.6px → 判 TRUE 实际超界 → crowd bound 全灭 → 倒置对 → 左推趟级联回退，重叠从一对搬到另一对）；②漏**跨小节入链**（crowd 跨小节贯穿后 per-measure 模拟少算前小节尾占位）；③漏 **dup 错开占位**；④豁免判据只查"链尾越界"漏**保位互叠**（delta=0 时链尾不越界但组间互叠，违例爆回 4.7 万）。
- 规则 22：**宽度判据必须完全复刻实际排布趟的每一步**（dup 错开步长 → 跨小节贯贯链 → 组粒度右推 + bound 保位 → 行首偏移），任何简化（per-measure、忽略 dup、忽略偏移）都会在"余量 < 差量"的边界 case 判错方向。实现方式：`rowOverfull` 行级模拟与 crowd 趟同构，折行 rowFits 与探针豁免共用同一判据（口径漂移即失效）。豁免的互叠口径用**探针同款**（缺口 >2px = dx < 墨半和-1 必违例），不用 crowd 的 need>0（会把 0.5px 贴边也豁免掉）。

## 2026-11-17 GP3/GP4/GP1/2 击勾标志语义反转（用户 gp8 对照实证）
- 场景：哆啦A梦.gp3 击勾弧整体前移一音（出现 7→7 同品怪弧），用户截图实证 gp8 的弧是 10→9/7→9/10→9/7→9——弧起点恰为**带标志音**。TuxGuitar/PyGuitarPro 把 GP3 hammer 标志读作 destination（标志音=弧终点），与 gp8 相反；gp8 的老格式读取器（v1-4 单路径）按 origin 处理。
- 规则 23：**老格式（GP1/2/3/4）hammer 标志 = origin 语义**（标志音=弧起点，弧到同弦下一音）；GP5/gpx 通道有显式 HopoOrigin/Destination 属性、走独立解析路径且经走查验证——**两套语义并存，不许互相"修正"**。对账测试比较的是"文件在哪个音上有标志"（py 侧同位），语义差异在渲染层处理。用户"重新导入没变化"的另一教训：**构建 exe 时旧实例还开着 = 重导入走的还是旧代码**——验证前必须彻底重启 app。

### 规则 33：拍号口径铁律——X/8 拍号≠分子个四分拍（2026-11-19 深夜三）

**事件**：Prologue“指针到了不响”三轮修复无效（tie 延长只“提前了一点”）。
根因：6/8 拍号小节被按分子计 6 个四分拍（4.8s），音符四分拍口径只占 3 拍
→ 每小节末 2.4s 空白 48 段 + 播放头爬出小节盒 snap 回下一小节（用户描述
“小节末指针返回才响”逐字命中）。

**教训链**：
1. **拍号 N/D 的小节四分拍数 = N×4/D**（6/8=3、12/8=6、2/2=4），不是
   分子 N。音符 beat/duration 全 IR 四分拍口径，播放时间轴/播放头线性轴
   必须同口径。唯一事实源 `score_ir.measureQuarterBeats`。
2. **视觉轴≠时间轴**：tab_layout.beatsOfBar（分子）服务视觉盒宽 +
   contentBeats 平铺（渲染正常），linearStarts（四分拍）服务播放头——
   两轴并存时必须显式命名区分（linearBeatsOfBar），注释写明各服务谁。
3. **“自洽假象”陷阱**：两处同错（播放轴+播放头轴都按分子）相互抵消，
   离线轴 dump 看着“全对齐”——上一轮诊断据此误判“轴全自洽”并把拍号
   误记成 3/4。判据要从**谱面第一性**（拍号 6/8 → 3 四分拍 × tempo）核，
   不能只看内部一致性。
4. **用户描述逐字对应机制**：“指针返回到小节前才开始响” = snap-back
   现象的精确描述——用户现象每字都要有机制解释，解释不了的字段就是
   还有未发现的问题。

**检查清单**（改播放/布局拍相关代码时）：
- [ ] 新代码用 measureQuarterBeats，不手写 `split('/')[0]`
- [ ] 视觉宽（beatsOfBar）与线性轴（linearBeatsOfBar）没混用

### 规则 34：GP 装饰音（grace）数据形态与字节序（2026-11-19 深夜四）

**事件**：用户报 Prologue m4/m17"滑音漏掉/丢音/滑音结束音与其他拍音同
拍"——根因：GP3/4/5 的 grace 是**本体音上的 effect 数据**（装饰 fret +
transition + duration），解析层把 4/5 字节全丢弃 → 装饰音消失、本体被
grace 标志误画成小号装饰形态。

**教训链**：
1. **grace 两形态**：gpx/gpif = beat 级标志+独立音（装饰音是独立
   NoteIr）；GP3/4/5 二进制 = 本体音上的装饰**数据**（py 挂 Note.effect
   不算独立音）——统一落 IR 口径：合成为独立装饰 NoteIr（同拍
   grace=true 先于本体，本体 grace=false），渲染/播放层不区分来源。
2. **同一数据两格式字节序不同**：GP3 fret/vel/**durCode**/transition，
   GP5 fret/vel/**transition**/durCode/flags——凭"py 字段序"猜通用序
   翻车（m4 实锤 trans/dur 互换误映射）；每格式按 py 对应 parser 的
   readGrace 逐字节对齐。velocity 是编码值（16v-1 unpack）、duration
   是编码值（1<<(7-code)），都不是终值。
3. **丢字节的代价是连锁的**：数据层丢弃 → 显示层误形态（本体画成
   装饰）→ 排布层假违例（用户看到的"同拍"）——修 bug 先修数据源，
   上层症状自查是否数据丢失的影子。
